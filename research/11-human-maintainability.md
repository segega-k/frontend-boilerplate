## Summary (≤ 15 lines)
1. Цель: человек без ИИ проходит «симптом → файл → правка → выкладка/откат» за 30 минут. Сейчас в бойлерплейте
   документов для людей нет вообще: только AI-доки на английском.
2. xRocket (замеры): путь до 16 сегментов, 85 файлов на одну страницу, DI через декораторы tsyringe с регистрацией
   побочным эффектом импорта, 7–9 прыжков от экрана до запроса, своё MVVM-правило отключено 233 раза, `Routes.tsx`
   1196 строк, `CLAUDE.md` 61 KB как «вход для человека», деплой в чужом репо, ни runbook, ни отката, ни
   ErrorBoundary, ни request id. Хорошо: build-info + Sentry release, hidden source maps, комментарии «почему».
3. Две документации: человеческая (`README` → `docs/runbooks/EMERGENCY.md`, `ARCHITECTURE.md` ≤ 300 строк,
   `apps/<app>/README.md` с картой «где X», `docs/adr/`) и ИИ (`CLAUDE.md` ≤ 200 строк + `docs/ai/` или
   `.claude/rules/`). Один факт — один источник, ИИ-доки ссылаются на человеческие. CI проверяет, что пути из доков
   существуют.
4. Runbooks: deploy, rollback (только сменой образа по SHA), hotfix (от прод-тега, `pnpm check:hotfix`),
   dependency-broken, api-down (рубильник maintenance), white-screen, config-env. Формат: когда → проверить →
   сделать → убедиться → эскалация. Раз в квартал прогон без ИИ.
5. Пределы магии: нет DI-контейнера и декораторов, нет шины событий, кодген только OpenAPI/иконки (результат и
   схема коммитятся, `linguist-generated`), ≤ 4 прыжков от страницы до сети, путь ≤ 6 сегментов, свои lint-правила с
   лимитом отключений.
6. Встроенная отладка: `/version.json` = Sentry release = тег образа; hidden source maps; ErrorBoundary на маршрут с
   блоком «детали для поддержки»; `X-Request-Id` на каждый запрос; `log.*` вместо `console`; `?debug=1`;
   рубильники в `/config.json` без пересборки, у флагов owner и `expires`.
7. Чек-лист ревью ИИ-кода (13 пунктов) и аварийный чек-лист человека (9 шагов) — готовы к переносу в docs.
8. Главное противоречие с текущими правилами: абсолютный запрет комментариев. Предложение: запрет «что», разрешение
   «почему» в 4 случаях. Остальные напряжения (мелкие файлы, MVVM, lint) решаются плоскостью и лимитами без отмены
   правил пользователя.

### F2. Что уже есть в бойлерплейте и что мешает человеку
- Вся документация (`CLAUDE.md` 6 KB + `docs/*.md` ~78 KB) — AI-facing, на английском, в императиве для агента («Do only what was asked», git-правила сессии). Человеческих документов нет: ни ARCHITECTURE, ни runbook, ни ADR, ни «где что лежит». README — маркетинговое описание концепции.
- `docs/architecture.md` §1 уже правильно отказался от 6 FSD-слоёв, barrel на каждый слайс, god-routes и `CONTEXT.md` на папку. Это совпадает с интересами человека.
- Но сохранена сложность, опасная для человека: MVVM «store / view model / page root / page view» с правилом «view model never navigates, exposes a signal, view resets it» (§3, §6) и упоминание DI в library-notes. Для ночного дебага это лишние прыжки.
- `code-style.md` §2 «No new comments» абсолютен — запрещает и «почему»-комментарии, которые человек больше всего ценит в чужом коде.
- `code-style.md` §1 «one component per file, types/consts/utils рядом, ui/<Sub>/» + 200 строк на `.tsx` при отсутствии лимита глубины воспроизводит путь xRocket `ui/X/ui/Y/ui/Z` (проблема F1-1).
- Есть хорошие заделы: request id в тексте ошибки (§5), runtime env injection, теги деплоя `<env>-<timestamp>` (tooling §9), правило «каждое правило — проверка или явно manual».

### F3. Внешние источники (подробно с цитатами — в `research/11a-web-human-maintainability.md`)
- **Когнитивная нагрузка, локальность.** Рабочая память ~4 чанка; мелкие модули и глубокие цепочки вызовов
  увеличивают нагрузку («deep modules», Ousterhout) — https://github.com/zakirullin/cognitive-load ,
  https://github.com/johnousterhout/aposd-vs-clean-code ; Locality of Behaviour — https://htmx.org/essays/locality-of-behaviour/ ;
  colocation — https://kentcdodds.com/blog/colocation . Вывод: важна не «длина файла», а число мест, которые нужно
  держать в голове, — отсюда лимиты прыжков и глубины (R5), а не отмена «одного компонента на файл».
- **CLAUDE.md.** Официально: < 200 строк на файл, правила для части кода — в `.claude/rules/*.md` с `paths:`,
  обязательное — хуками, а не текстом; «Bloated CLAUDE.md files cause Claude to ignore your actual instructions» —
  https://code.claude.com/docs/en/memory , https://code.claude.com/docs/en/best-practices . 61 KB xRocket вредят и
  агенту, а не только человеку.

  ARCHITECTURE.md с codemap и инвариантами «через отсутствие», «имена, а не ссылки» — https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html

- **ADR.** MADR 4.0 (минимальный вариант) — https://adr.github.io/madr/ . Раздел «отклонённые альтернативы» нужен
  именно против агентов, которые «чинят» принятые решения.
- **Runbooks.** Google SRE: заранее записанный playbook даёт ~3× лучше MTTR, чем импровизация —
  https://sre.google/sre-book/introduction/ , https://sre.google/workbook/on-call/ .

  не отключать — https://docs.sentry.io/platforms/javascript/session-replay .
- **Флаги.** Таксономия release/ops/experiment/permission (Fowler, 2016, канон) — https://martinfowler.com/articles/feature-toggles.html ;
  Unleash: ожидаемое время жизни release 40 дней, operational 7, kill switch бессрочно — https://docs.getunleash.io/reference/feature-toggle-types ;

## Recommendations for the boilerplate

Главный принцип: **человек ночью должен пройти путь «симптом → файл → правка → выкладка» за 30 минут, без ИИ, без
доступа к внутренним инструментам и не читая правил для агента.** Каждое правило ниже служит этому пути.

### R1. Две документации: для людей и для ИИ (P0)

| | Для людей | Для ИИ |
|---|---|---|
| Вопрос, на который отвечает | «Как это устроено? Где X? Что делать, когда сломалось? Почему так решили?» | «Как писать код здесь, чего нельзя, как работать с пользователем» |
| Жанр (Diátaxis) | explanation (ARCHITECTURE), how-to (runbooks), reference (карта «где X»), решения (ADR) | reference + правила в императиве с причиной |
| Где лежит | `README.md`, `ARCHITECTURE.md`, `docs/runbooks/`, `docs/adr/`, `apps/<app>/README.md` | `CLAUDE.md`, `docs/ai/*.md` (нынешние `docs/*.md` переезжают сюда), `.claude/` |
| Язык | язык команды (по умолчанию русский, см. вопрос 2) | английский (как сейчас) |
| Размер | README ≤ 1 экран до раздела «Запуск»; ARCHITECTURE ≤ 300 строк; runbook ≤ 1 экран (≈ 60 строк); ADR ≤ 1 страница | `CLAUDE.md` ≤ 200 строк (официальная рекомендация Anthropic, F3), остальное в `.claude/rules/*.md` с `paths:` или skills; проверка `wc -l` в CI |
| Точка входа | `README.md` → раздел «Если прод упал» — первая ссылка | `CLAUDE.md` |

Правила:
1. **Один факт — один источник.** ИИ-доки ссылаются на runbooks и ADR, а не пересказывают их. Пример: правило «откат
   только сменой тега образа» живёт в `docs/runbooks/rollback.md`, `CLAUDE.md` даёт ссылку.
2. **Человеческие доки не содержат правил для агента** (git-этикет сессии, формат отчёта, цитаты пользователя). ИИ-доки
   не являются входом для человека: в xRocket README отправлял человека в 61 KB `CLAUDE.md` (F1-6).
3. **Ни одного `CONTEXT.md`/README на папку** (подтверждено 06 §1.7: устаревают). Исключение: `apps/<app>/README.md` —
   карта приложения; init удаляет её вместе с приложением.
4. **Проверка дрейфа в CI** (`scripts/check-doc-paths.mjs`, ~40 строк на `node:fs`): каждый путь в обратных кавычках в
   `README.md`, `ARCHITECTURE.md`, `docs/runbooks/*`, `apps/*/README.md` должен существовать; каждая команда
   `pnpm <script>` из runbook должна быть в `package.json`. Это закрывает главный провал xRocket — ссылки на
   несуществующие файлы.
5. **Runbook проверяется игрой**: раз в квартал (или при смене деплоя) человек без ИИ проходит `rollback.md` на
   staging; дата прохода пишется в шапке runbook (`Last drill: 2026-10-14`).

### R2. Карта «где X» (P0)

Корневой `ARCHITECTURE.md` (стиль matklad: птичий полёт, codemap, инварианты, без деталей, которые быстро устаревают):
1. Абзац «что это за система» и картинка-схема «браузер → наш фронт (nginx/SSR) → внешний API / провайдеры».
2. Codemap верхнего уровня: `apps/*`, `packages/ui`, `packages/tokens`, `packages/api`, `packages/config`, `tools/`,
   `docs/`.
3. **Инварианты** (то, что нельзя увидеть в коде, потому что это отсутствие чего-то): «`packages/ui` не импортирует
   приложения», «вне `packages/api` нет `fetch`», «деньги только через decimal», «нет DI-контейнера».
4. «Сквозной путь запроса» в 5 строк: URL → таблица маршрутов → страница → query-хук → функция API → generated client.

Каждое приложение — `apps/<app>/README.md` с таблицей «Хочу найти / Где лежит / Как проверить». Общие строки для всех
шаблонов (пути условные, фиксируются после выбора стека):

| Хочу найти | Где | Как проверить |
|---|---|---|
| Какой файл рисует URL `/x/y` | `src/app/routes.ts` (таблица, один файл на приложение, ≤ 200 строк) → `src/domains/<d>/pages/<Page>/` | открыть URL с `?debug=1`: в консоли имя страницы |
| Откуда берётся base URL API, ключи | `src/shared/config/env.ts` + `.env.example`; в рантайме `/env.js` контейнера | `window.__ENV__` в консоли |
| Вызов конкретного эндпоинта | `packages/api/src/<service>.ts` (руками) поверх `packages/api/generated/<service>.ts` | поиск по пути эндпоинта `'/v1/orders'` |
| Текст ошибки для эндпоинта | `packages/api/src/errors/map.ts` | поиск по коду ошибки |
| Тексты интерфейса | `src/shared/i18n/<lang>/<ns>.json` | поиск по видимой фразе |
| Цвета, отступы, темы | `packages/tokens/` | — |

### R3. Runbooks (P0): `docs/runbooks/`

Формат каждого (≤ 1 экран, команды копируются как есть):

```
# <Название>
Last drill: <дата>   Owner: <роль>
## Когда применять        симптомы, 1–3 строки
## Проверить              команды/URL, что увидеть
## Сделать                нумерованные шаги, каждая команда в блоке
## Убедиться              как понять, что помогло
## Если не помогло        следующий runbook или кого звать
```

Обязательный набор (содержание — минимально достаточное, стек-агностично; конкретные команды init подставляет под
выбранный CI):

1. **`deploy.md`.** Выкладка = git-тег `<env>-<YYYYMMDD-HHMM>` → CI собирает **один образ** с тегом = короткий SHA
   (неизменяемый; в реестре включить immutable tags) → тот же образ продвигается staging → production; env подставляется при старте контейнера (`env.js`),
   не при сборке. Проверить: `/version.json` показывает новый SHA, smoke-страницы отдают 200.
2. **`rollback.md`.** Откат = выкладка **предыдущего образа**, без пересборки и без revert в git (это второй шаг, днём).
   Команды на выбор шаблона: `kubectl rollout undo deploy/<app>` / `helm rollback <release> <rev>` / для compose —
   `IMAGE_TAG=<prev-sha> docker compose up -d <app>`. Где взять предыдущий SHA: список тегов в реестре или
   `deploy/RELEASES.md`, куда CI дописывает строку на каждый прод-деплой (дата, SHA, кто). Убедиться: `/version.json`.
   Пометка: chunk-файлы старой версии должны остаться доступны (nginx отдаёт `index.html` без кэша, ассеты с хешем —
   `immutable`; lazy-import с retry и перезагрузкой при ошибке чанка уже в architecture.md §9).
3. **`hotfix.md`.** Ветка `hotfix/<коротко>` от **прод-тега**, не от main → минимальная правка → `pnpm check` →
   PR/MR с пометкой hotfix (один ревьюер или пост-фактум ревью) → тег прод-выкладки → черри-пик/merge в main. Какие
   проверки можно пропустить в аварии (визуальные тесты, e2e кроме smoke) и какие нельзя (typecheck, build, unit).
   Скрипт `pnpm check:hotfix` делает ровно разрешённый набор, чтобы человеку не надо было выбирать.
4. **`dependency-broken.md`.** Симптом: сборка падает на чистом CI без изменений кода. Шаги: `pnpm install
   --frozen-lockfile` (lockfile — истина; без него не ставить); сравнить `git diff <последний зелёный>..HEAD --
   pnpm-lock.yaml`; откатить lockfile; при сломанной транзитивной версии — `overrides` в `pnpm-workspace.yaml` с
   комментарием-ссылкой на issue и датой снятия; `minimumReleaseAge` уже защищает от свежих релизов (tooling.md §1).
   Образ CI на фиксированном digest Node.
5. **`api-down.md`.** Симптом: массовые 5xx/таймауты. Проверить: health эндпоинт бэкенда, процент ошибок по
   эндпоинтам в Sentry. Фронт не чинит бэкенд; сделать: включить рубильник `maintenance` (или отдельные `kill.<feature>`)
   в `/config.json` без пересборки → пользователи видят экран «технические работы» вместо сломанных форм. Текст для
   эскалации на бэкенд (шаблон с request id и временем).
6. **`white-screen.md`** (дополнительно, частый фронтовый инцидент): кэш `index.html`, ошибка чанка после выкладки,
   ошибка в провайдере до ErrorBoundary, CSP. Как прочитать ошибку с прод-source maps (Sentry), как воспроизвести
   локально на прод-образе: `docker run -p 8080:80 <image>:<sha>`.
7. **`config-env.md`**: где лежат переменные каждого окружения, как поменять без пересборки, как проверить `/env.js`.
8. **`secrets-leak.md`** — ссылка на отчёт 10 (security), если он даёт процедуру.

### R4. ADR (P1): `docs/adr/NNNN-<kebab-title>.md`

Формат (MADR-lite, ≤ 1 страница):

```
# NNNN. <Решение в форме утверждения: «Нет DI-контейнера»>
Status: accepted | superseded by NNNN | deprecated     Date: 2026-10-14
## Контекст          что болело, с фактами (ссылки на код/инциденты)
## Решение           одно-два предложения
## Последствия       что становится проще, что сложнее, что запрещено
## Альтернативы      1–3 строки на каждую и почему нет
## Как проверяется   lint-правило / тест / ревью (manual)
```

Когда писать (любой пункт):
- выбор или замена библиотеки уровня приложения (state, роутинг, UI-кит, query, формы, i18n, сборщик);
- запрет или исключение из правила архитектуры (например, «здесь разрешён импорт домен → домен»);
- всё, что неочевидно из кода и будет «исправлено» следующим человеком или агентом (то, что сейчас попадает в
  «Deliberate, do not fix» в workflow.md §11 — на уровне проекта это и есть ADR);
- решение, после которого откат дороже недели работы.

Не писать: выбор имени, мелкий рефакторинг, то, что уже выражено типами/линтом.

Порядок: ADR неизменяем после `accepted`; изменение = новый ADR со `supersedes`. Агент пишет черновик ADR как часть
плана крупной задачи (workflow.md §5), человек принимает. Бойлерплейт поставляется с 8–12 стартовыми ADR из уже
принятых решений: монорепо с несколькими шаблонами, только фронтенд, Docker на своих серверах, без RN, домены вместо
FSD-слоёв, без DI-контейнера, сгенерированный API-клиент коммитится, рубильники через runtime config, политика
комментариев. Это одновременно объясняет человеку «почему так».

### R5. Пределы магии и косвенности (P0)

| Механизм | Правило | Почему (xRocket) |
|---|---|---|
| DI-контейнер (tsyringe, inversify), декораторы | **Нет.** `experimentalDecorators` и `emitDecoratorMetadata` выключены, `reflect-metadata` в запрещённых зависимостях. Зависимости: обычный `import` модуля-синглтона или явный аргумент конструктора / React context с типом. Тестовые фейки — через аргумент | F1-2: регистрация побочным эффектом импорта, ошибки только в рантайме; legacy-декораторы не совпадают с TC39-декораторами и требуют отдельной трансформации в Vite/esbuild |
| Глобальная шина событий, `CustomEvent` на `document`, строковые ключи регистрации | **Нет.** Связь «кто вызывает → кого» должна находиться через Go to Definition. Состояние «maintenance» — поле стора/контекста | F1-11 |
| Кодогенерация | Только (1) типы/клиент из OpenAPI, (2) иконки, (3) route-типы, если их требует роутер. Всё в папках `generated/`, заголовок `AUTO-GENERATED by <script>, do not edit`, `.gitattributes`: `**/generated/** linguist-generated=true -diff` (свёрнуто в ревью), исключено из поиска в `.vscode/settings.json` (`search.exclude`). **Результат коммитится**, исходная схема (`openapi/<service>.json`) тоже коммитится, генератор запускается `pnpm api:generate` из репо без внешних доступов | F1-7: человек ночью не может перегенерировать без «xRocket Tools» |
| Proxy/метапрограммирование, `cloneElement`-контейнеры, HOC-цепочки | Только внутри библиотек (MobX и т. п.). Своё — нет; HOC не глубже одного | workflow.md §4 уже запрещает «containers with hidden magic» |
| Barrels | `index.ts` только у пакета (`packages/*`) и домена; без `export *` (уже в architecture.md) | F1: 300 `index.ts` в xRocket |
| Свои ESLint-правила | Каждое: сообщение с причиной и ссылкой на якорь doc; RuleTester-тест. **Правило, которое выключено > 10 раз, либо чинится, либо удаляется** (CI-скрипт считает `eslint-disable <rule>`). `eslint-comments/require-description` — каждый disable с причиной | F1-4: 233 отключения своего MVVM-правила |
| Глубина косвенности | **≤ 4 прыжка Go to Definition от страницы до сетевого вызова**: `Page` → `useXxxQuery` (или VM) → `api/<service>.ts` → `generated`. Обёртка, которая только пробрасывает, удаляется | F1-3: 7–9 прыжков |

Проверка — тот же architecture-тест на `node:fs` | F1-1: максимум 16 |
| God-файлы | Лимиты уже есть (200/700 строк); `max-lines` disable запрещён без ADR | F1-5 |

### R6. Имена и локальность (P1)

1. **Имя файла = имя экспорта = то, что видно в стектрейсе/DevTools** (`OrderDetailsPage.tsx` экспортирует
   `OrderDetailsPage`). Никаких `index.tsx` с компонентом, никаких одноимённых `model.ts` в 60 местах — `ordersQueries.ts`,
   `OrderDetailsViewModel.ts`.
2. **URL ↔ папка.** Маршрут `/orders/:id` → `domains/orders/pages/OrderDetails`. Человек из адресной строки за один
   поиск находит экран.
3. **Grep-уникальность.** Коды ошибок, ключи флагов, event-имена аналитики, `data-testid` — строковые литералы в одном
   месте и уникальны: поиск по тексту из Sentry или из жалобы ведёт в один файл.
4. **Колокация по изменению**: то, что меняется вместе, лежит вместе — страница, её запросы, её тексты-ключи, её
   тесты и stories в папке страницы. Общее поднимается в `shared` только при втором реальном потребителе (правило
   трёх для абстракций — при третьем).
5. **Ничего важного по соглашению имён без проверки.** Если поведение зависит от суффикса файла (`.web.tsx`), это
   записано в ARCHITECTURE и проверяется.
6. **Комментарии «почему»** (см. T1): разрешены и ожидаемы для workaround'ов (ссылка на issue), неочевидного порядка,
   денег/безопасности, чисел из внешних спецификаций. Комментарии «что делает код» запрещены.

### R7. Средства отладки, встроенные в шаблон (P0)

1. **Build info**: `/version.json` (`version`, `sha`, `builtAt`, `env`), `<meta name="build">`, Sentry `release` с тем
   же значением (как `write-build-info.mjs` xRocket, вынести в `tools/` бойлерплейта).
2. **Source maps**: генерируются как `hidden`, загружаются в self-hosted Sentry/GlitchTip в CI и **удаляются из
   образа** (`filesToDeleteAfterUpload`, плюс nginx `location ~* \.map$ { return 404; }`). Session replay выключен, при
   включении — только on-error и с масками. Человек читает прод-стектрейс с именами файлов.
3. **ErrorBoundary на уровне каждого маршрута** + корневой. Экран ошибки показывает: что случилось простыми словами,
   кнопку «повторить», и сворачиваемый блок «Детали для поддержки» (release, route, время, последний request id) с
   кнопкой «Скопировать». В Sentry: теги `app`, `domain`, `route`, `release`.
4. **Request id**: middleware API-клиента ставит `X-Request-Id` (UUID v7) на каждый запрос, кладёт его в Sentry
   breadcrumb и в объект ошибки; если бэкенд поддерживает трассировку — также `traceparent` (W3C). Тексты ошибок
   (architecture.md §5) показывают этот id.
5. **Логгер** `src/shared/lib/log.ts`: уровни, префикс домена, в проде по умолчанию только `warn/error` → Sentry
   breadcrumbs; `?debug=1` (или `localStorage.debug`) включает подробный вывод, панель с версией, активными флагами,
   текущим маршрутом. `console.log` в коде запрещён, только `log.*`. (Уточнение к code-style.md §4, где сейчас
   «console.log только в catch».)
6. **Рубильники (kill switches) и режим обслуживания**: реестр `flags.ts` — ключ, описание, владелец, дата удаления
   (`expires`); значения из `/config.json`, который nginx отдаёт без кэша и который можно поменять без пересборки
   (volume/ConfigMap). CI падает на флаге с истёкшим `expires`. Флаг `maintenance` переключает приложение в экран
   «технические работы» на уровне composition root (architecture.md §5 «fatal app states»). Внешний флаг-сервис —
   только если проекту он нужен (вопрос 4).

### R8. Как держать ИИ-код читаемым для человека: чек-лист ревью (P0)

Встраивается в ревью-агента (workflow.md §6) **и** в шаблон MR/PR для человека:

1. Могу ли я за 2 минуты найти, откуда пришли данные на экране, только через Go to Definition?
2. Нет ли новой абстракции с одним потребителем (обёртка, фабрика, generic-хелпер, «на будущее»)?
3. Нет ли проброса без логики (метод/хук/компонент, который только передаёт дальше)?
4. Нет ли дублей существующих хелперов/компонентов (ИИ копирует охотнее, чем переиспользует)?
5. Нет ли «защитного» кода без причины: `try/catch`, который глушит, `?? []` на обязательных данных, проверки
   невозможных состояний, `as`-касты?
6. Имена говорят о предмете (не `data`, `item`, `handleClick2`, `utils2`)?
7. Новые файлы лежат там, где их ищет человек по карте R2; глубина ≤ 6; нет `ui/X/ui/Y`?
8. Есть ли неочевидное решение без «почему» (ни комментария, ни ADR)?
9. Новые `eslint-disable` — каждый с причиной; новые зависимости — с причиной в описании PR?
10. Diff меньше 400 строк логики (без generated/lockfile/переводов); иначе разбить.
11. Сгенерированное не редактировалось руками; generated-изменения отделены в свой коммит.
12. Ошибки не потеряны: API-ошибки идут через маппинг, исключения доходят до Sentry с контекстом.
13. Удалённая фича удалена целиком (флаги, тексты, стили, тесты).

### R9. Аварийный чек-лист для человека без ИИ (P0)

Файл `docs/runbooks/EMERGENCY.md`, ссылка первой строкой в README:

1. **Не чините сразу.** Что видит пользователь, с какого времени, всё ли приложение или один экран?
2. **Что выкачено?** `curl https://<host>/version.json` → SHA и время. Совпадает ли начало проблемы с выкладкой →
   если да: **сначала откат** (`rollback.md`), разбор потом.
3. **Это мы или API?** DevTools → Network: 5xx/таймауты от API → `api-down.md` (рубильник `maintenance`, эскалация с
   request id). Ошибки JS / белый экран → `white-screen.md`.
4. **Ошибка в Sentry**: фильтр по `release` текущей версии, читать стектрейс (source maps уже там), теги `route`,
   `domain` → карта R2 в `apps/<app>/README.md` → файл.
5. **Воспроизвести локально на прод-образе**: `docker run` с тем же SHA, или `pnpm i --frozen-lockfile && pnpm dev`
   на прод-теге.
6. **Правка = hotfix** (`hotfix.md`): ветка от прод-тега, минимальное изменение, `pnpm check:hotfix`, выкладка тегом.
7. **Можно выключить?** Рубильник `kill.<feature>` в `/config.json` без сборки — быстрее любого фикса.
8. **Запишите** в `docs/incidents/YYYY-MM-DD-<коротко>.md` (5 строк: что, когда, причина, что сделали, что
   доделать днём). Утром — постмортем и, если надо, ADR.
9. Контакты: кто владеет бэкендом, инфраструктурой, доменом/DNS, Sentry (таблица в README, заполняется при init).

### R10. Шаблоны и автоматизация (P1)
- `pnpm doctor`: проверка Node/pnpm версий, наличия `.env`, доступности API base URL, совпадения `.nvmrc` и Docker.
- `pnpm where <url>` (небольшой скрипт по таблице маршрутов): печатает файл страницы для URL — прямая помощь человеку.
- Init дописывает в `README.md` таблицу контактов и окружений, удаляет карты и runbook-строки невыбранных шаблонов.

|---|---|---|---|

Тогда «много файлов» = одна папка, которую видно целиком |
| T3 | Store / view model / page root / page view, VM не навигирует, сигналы | Лишние прыжки и свой lifecycle | Слой VM только для экранов с реальной оркестрацией; простые экраны — query-хук + компонент (architecture.md уже допускает «stateless page без VM» — расширить на «простой экран с запросами»). VM создаётся явно (`new XViewModel(deps)` в хуке), без контейнера |
| T4 | Много своих lint-правил как ограждения для ИИ | Человек не знает, что правило значит; массовые отключения | Сообщение с причиной + ссылкой; лимит отключений (R5); правила, которые человеку мешают в аварии, не входят в `check:hotfix` (кроме typecheck/build) |
| T5 | Процесс «никогда без запроса не коммить, не обходить хуки» | В аварии человеку нужен быстрый путь | Это правила **для агента**. Для человека — runbook `hotfix.md` с явно разрешённым сокращённым набором проверок; хуки не обходятся, а `check:hotfix` и есть набор для хука |
| T6 | Большой единый контекст для агента | Человек не может это читать | AI-доки — не вход для человека (R1.2). `CLAUDE.md` ≤ 200 строк, детали по задачам |
| T7 | Кодген ускоряет ИИ | Генераторы с внешним доступом, шум в поиске | Коммитить результат и схему, `linguist-generated`, `search.exclude` (R5) |
| T8 | «Reuse before writing» → ИИ строит общие абстракции | Обобщения с одним потребителем | Поднимать в shared при втором потребителе, абстрагировать при третьем; чек-лист R8.2 |
| T9 | Английский для ИИ-доков | Человек в стрессе читает быстрее на родном | Человеческие доки на языке команды (вопрос 2); ИИ-доки ссылаются на них, ИИ умеет читать русский |

## Open questions for the user
1. **Комментарии.** Смягчить «No new comments» до «запрещены комментарии "что", разрешены короткие "почему"» в четырёх
   случаях: workaround со ссылкой на issue, неочевидный порядок, деньги/безопасность, число из внешней спецификации
   (T1)? Без этого единственным носителем «почему» остаются ADR и чат, который человек ночью не увидит.
2. **Язык человеческих документов** (README, ARCHITECTURE, runbooks, ADR): русский (язык команды, быстрее в стрессе)
   или английский (если в проекты придут нерусскоязычные подрядчики)? ИИ-доки остаются английскими.
3. **MVVM по умолчанию или по необходимости.** Оставить «store / view model / page view» обязательным для каждого
   экрана или разрешить простым экранам «query-хук + компонент», а VM — только при реальной оркестрации (T3)? И
   подтвердить: без DI-контейнера, VM создаётся явно.
4. **Флаги.** Достаточно ли рубильников в runtime `/config.json` (без внешнего сервиса), или нужен self-hosted
   Unleash/GrowthBook для A/B и процентных выкаток?
5. **Аварийный путь человека.** Согласны ли на `pnpm check:hotfix` (typecheck + unit + build, без визуальных и
   полного e2e) как официально разрешённый набор для hotfix, и на ревью hotfix пост-фактум?
6. **Где деплой.** CI-шаблоны и описание выкладки живут в этом репозитории (а не в общем infra-репо, как в xRocket)?
   Иначе runbook rollback не самодостаточен.
